# Manage Agent Run Context by Projected Token Budget

Foreground and User Schedule Agent Runs use one context-budget policy before the run and before every ReAct request. Available Context is `context_window - max_output`; the Compaction Context Window is the ceiling of Available Context multiplied by `[runtime].compact_ratio`. The ratio defaults to `0.9` and accepts finite non-Boolean values from `0.5` through `0.95`; missing or invalid values follow the shared default-value contract in [ADR-0025](0025-ignore-unknown-user-configuration-fields.md). The raw User Configuration is not rewritten by this fallback. Message count does not trigger compaction. Dream is not an Agent Run and follows [ADR-0024](0024-use-one-shot-dream-model-request.md).

Projected Next-request Usage first uses the latest main Agent assistant's compatible Reported Model Usage `total_tokens` plus the locally estimated context delta, including Tool Exposure changes. The latest assistant is a provenance boundary: when its usage provenance is missing, malformed, or unsupported, projection uses a complete local estimate instead of searching an older assistant. Projection never accumulates overlapping assistant `input_tokens`, which already include the request's User and Tool messages, and it also falls back to a complete local estimate when route, provider, model, estimator, or anchor provenance is incompatible. Session cumulative usage remains observational. The separate 10% and 50% retention calculations include only the target Agent Run's uncompacted raw User, assistant, and Tool messages; compatible snapshot differences may be used only when all non-run inputs, including Tool Exposure, are unchanged.

At Run start, multiple uncompacted completed runs retain the newest run only when its slice is at most 10% of Available Context; otherwise all eligible history is selected. A sole eligible completed run is selected in full. During ReAct, the current run is retained when its slice is at most 50%; otherwise it may be selected, but the latest completed ReAct Cycle's assistant and Tool messages remain in the request. A selected current User advances the staged cursor normally and is temporarily re-projected exactly once for the rest of that Agent Run without being summarized or persisted twice.

Each Model Request Context revision is checked at most once. Reaching the Compaction Context Window triggers the maximum history compaction allowed by the retention rules. A result still at or above that soft threshold may proceed when it remains below Available Context; any model-visible input change creates a new revision. A final projection at or above Available Context fails with `model_context_overflow`. Every Provider attempt, including a dynamic fallback, repeats the hard check against that attempt's actual Model Route; a smaller fallback that cannot fit fails without starting nested history compaction or extra Summary calls.

Fact Summary receives only the newly selected original messages, including complete Tool Results, and is appended to the Workspace summary stream. Action Summary receives its previous staged value plus that same new selection and returns the complete rolling replacement; a normalized `None` clears it. Action Summary remains Session metadata, is projected as one plain user message after the System Prompt and before retained history, and enters neither the Workspace summary stream nor Session messages. Each summary performs one logical `memory` Model Router call and relies only on Router-level automatic retries. Fact persistence may remain when Action generation fails, but the failed step does not advance its staged cursor or Action Summary. Agent Run-owned pending cursor, Action Summary, compaction usage, and latest usage snapshot commit with the terminal run increment; the current-User projection state remains run-local and is discarded at that terminal boundary. Agent Runner remains Session-independent and the Summary stream remains outside the Session transaction.

Tool Result Micro-compression starts only after an Agent Run completes more than ten eligible Tool Calls. It replaces completed success, error, or refused results longer than 512 characters from prior Agent Runs and earlier ReAct Cycles of the current run for `exec`, `glob`, `grep`, `list_dir`, `read_file`, `web_fetch`, `web_search`, and recognized MCP Tools with `[tool_name result omitted from context]`. The latest completed Cycle stays complete, and replacement is Provider-only. When both mechanisms apply, history compaction and both summaries see complete Tool Results first; only then is micro-compression re-evaluated against the retained request projection. Persisted messages, AgentRunner results, Tool Artifacts, and summaries never contain placeholders. This consolidates the still-valid parts of superseded ADR-0022.

Runtime status is a side-effect-free projection based only on the currently committed Conversation Session and current User Configuration. It describes the configured initial `chat` Model Route for the next independent Foreground Agent Run, including the configuration-level static `default` when `chat` is not declared. A dynamic fallback is local to one logical Router call and does not become the initial Route of a later call; Runtime status neither reports uncommitted in-flight ReAct state nor reuses a prior call's fallback Route.

Runtime status obtains its budget values from the same projection and exposes exactly these context fields: `context_window` is the route's total context window; `max_output` is its reserved output ceiling; `available_context` is `context_window - max_output`; `compact_ratio` is the effective finite ratio; `compact_context_window` is `ceil(available_context * compact_ratio)`; `projected_next_request_tokens` is the next request's projected input size; `projection_source` is `reported_delta` when a compatible Provider usage anchor supplies the delta and `estimated` when the complete request is estimated locally; and `input_budget_used_percent` is `projected_next_request_tokens / available_context * 100`. The percentage is therefore based on Available Context. Cumulative usage remains visible but is not a context-occupancy measure, and Schedule status is not part of these Foreground status fields.
